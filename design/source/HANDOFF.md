# HANDOFF.md — Courier Forecast / Ordinary Report App

## 1. Цель

Сделать отдельное мобильное приложение вместо обычной картинки-отчёта в чате.

Приложение нужно только для финансового контроля текущего расчётного периода:

- пользователь вручную вводит значения спидометра Яндекс Про;
- пользователь вручную вводит ежедневные выплаты и удержания;
- приложение само считает финансовый итог;
- приложение показывает текущий темп;
- приложение показывает, сколько ещё времени можно находиться оффлайн без новых заказов до критического порога выплат;
- приложение умеет выгружать готовый отчёт для ChatGPT, чтобы пользователь мог загрузить его в чат и обсуждать статистику.

RAW-отчёты сюда НЕ включать.

---

## 2. Что НЕ входит в приложение

Не переносить:

- RAW-отчёты;
- принятие/завершение отдельных заказов;
- магазины;
- busy/free time;
- расстояния отдельных заказов;
- прогноз спроса;
- погоду;
- модель прогноза по часам;
- анализ утренней/вечерней плотности;
- велосипедные акции Яндекс Про.

Велосипедная акция всегда игнорируется в финансах.

---

## 3. Расчётный период

- период: 14 дней;
- новый период начинается в пятницу;
- ставка: `360 ₽ × учитываемые часы`;
- критический порог выплаты: `1.80 заказа/ч`.

Никаких дополнительных «гонок» за 1.90, 1.85 и отдельных цветных целей в интерфейсе не показывать.

---

## 4. Главный экран

На главном экране показывать только основные цифры периода:

- даты текущего периода;
- часы на спидометре;
- заказы на спидометре;
- текущий темп;
- строку `Можно просидеть оффлайн без заказов`;
- общий доход;
- фактически выплачено;
- сколько ещё должен выплатить Яндекс;
- чаевые;
- отдельные бонусы;
- налог;
- комиссия парка.

### Текущий темп

Показывать одной строкой:

`Текущий темп: X,XXX заказа/ч`

Без дополнительных safe/critical pace карточек.

### Сколько можно просидеть оффлайн

Показывать одной строкой:

`Можно без заказов: X ч Y мин`

Эта строка считается до критического порога `1.80`.

Если запас исчерпан:

`Можно без заказов: 0 ч`

Обязательные поля:

- часы на спидометре Яндекс Про;

Налог и комиссию пользователь может вводить обычным положительным числом. В UI приложение само показывает их как удержание со знаком `−`.

## 6. Модель данных

```ts
type DailyFinance = {
  date: string
  periodId: string

  displayedHours: number
  displayedOrders: number

  reward: number
  tax: number
  parkCommission: number
  tips: number
  separateBonus: number

  displayedNet?: number
  finalAdjustment?: number

  note?: string
  createdAt: string
  updatedAt: string
}
```

Все финансовые составляющие хранить раздельно.

---

## 7. Финансовые формулы

### Почасовая база

`hourlyBase = displayedHours × 360`

### Уже выплачено Яндексом

`paidReward = сумма daily.reward внутри периода`

Только `Вознаграждение`.

Не включать:

- чаевые;
- отдельные бонусы;
- налог;
- комиссию;
- велосипедную акцию.

### Чаевые

`tipsTotal = сумма daily.tips`

### Отдельные бонусы

`separateBonusTotal = сумма daily.separateBonus`

Отдельные бонусы увеличивают общий доход пользователя, но не уменьшают задолженность Яндекса по почасовой базе.

### Общий доход

`grossUserIncome = hourlyBase + tipsTotal + separateBonusTotal`

Налог и комиссия парка из этой пользовательской формулы не вычитаются.

Отдельно показывать:

`taxTotal = сумма daily.tax`

`parkCommissionTotal = сумма daily.parkCommission`

### Сколько должен выплатить Яндекс

`estimatedYandexOwed = hourlyBase - paidReward`

При закрытии периода фактическая строка `Бонусы и корректировки / финальная доплата` сохраняется отдельно как факт.

Не добавлять её поверх `hourlyBase`.

---

## 8. Схема округления часов Яндекс Про

По накопленным данным наиболее вероятный механизм:

```text
displayedHours = floor(trueCumulativeHours)
```

То есть:

- спидометр показывает только целые завершённые часы;
- неполные минуты не пропадают;
- остаток минут переносится дальше;
- скрытый остаток всегда находится в диапазоне от 0 до 59 минут.

Пример:

`179 ч 37 мин` внутри системы отображаются как `179 ч`.

---

## 9. Текущий темп

Для цифры на главном экране использовать то, что реально показывает Яндекс:

`visiblePace = displayedOrders / displayedHours`

Это и есть строка `Текущий темп`.

Дополнительные темпы пользователю не показывать.

---

## 10. Формула «Можно просидеть оффлайн без заказов»

Чтобы не гадать скрытые минуты, использовать консервативный расчёт.

Пусть:

- `H` = отображаемые часы;
- `O` = отображаемые заказы;
- критический порог = `1.80`.

Худший возможный текущий знаменатель:

`conservativeHours = H + 59/60`

Максимально допустимые часы при текущем количестве заказов:

`maxHoursAtThreshold = O / 1.80`

Запас оффлайна:

```text
offlineReserveHours =
  max(0, maxHoursAtThreshold - conservativeHours)
```

То есть:

```text
offlineReserveHours =
  max(0, O / 1.80 - (H + 59/60))
```

UI переводит результат в часы и минуты.

Пример:

`1.75 часа` → `1 ч 45 мин`.

Это единственная строка запаса, которую нужно показывать пользователю.

---

## 11. Почему нельзя использовать дневную дельту спидометра как точные часы

Если вчера было `153 ч`, а сегодня `165 ч`, это не доказывает, что за день было ровно 12 часов.

Показание зависит от скрытого остатка минут вчера и сегодня.

Поэтому в истории подписывать:

`Изменение отображаемых часов: +12`

а не:

`Сегодня отработано 12 часов`.

- дата;

- изменение отображаемых часов;
- изменение заказов;

- отдельные бонусы;

## 13. Экспорт отчёта для ChatGPT

Это обязательная функция.

На главном экране нужна кнопка:

`Экспорт для ChatGPT`

После нажатия приложение формирует один файл, который пользователь может загрузить в ChatGPT.

Основной формат: **Markdown `.md`**.

Имя файла:

`courier-report-YYYY-MM-DD.md`

Дополнительно можно дать экспорт JSON, но Markdown обязателен.

### Что должно быть в экспорте

Экспорт должен быть самодостаточным и понятным новому чату без дополнительных объяснений.

Структура:

```md
# Courier Forecast Report

## Период
18.09.2026–01.10.2026

## Текущий спидометр
- Часы: 179
- Заказы: 345
- Текущий темп: 1.927
- Можно без заказов до 1.80: 11 ч 40 мин
- Скрытые минуты: неизвестны, расчёт запаса выполнен консервативно через +59 мин

## Финансы периода
- Почасовая база: ...
- Вознаграждение уже выплачено: ...
- Осталось выплатить Яндексу: ...
- Чаевые: ...
- Отдельные бонусы: ...
- Комиссия парка: ...
- Налог: ...
- Общий доход по пользовательской формуле: ...

## Дни
| Дата | Часы | Заказы | Δ часов | Δ заказов | Вознаграждение | Чаевые | Бонусы | Комиссия | Налог |
| ... |

## Правила расчёта
- ставка 360 ₽/ч;
- порог 1.80 заказа/ч;
- displayedHours = floor(trueCumulativeHours);
- скрытый остаток 0–59 минут;
- offlineReserve = max(0, orders/1.80 - (hours + 59/60));
- велосипедная акция не относится к доходу.
```

Не включать в этот экспорт RAW-заказы.

## 18. Валидация

Внутри одного периода нельзя:

- уменьшать cumulative hours;
- уменьшать cumulative orders;
- вводить отрицательный reward;
- вводить отрицательные чаевые;
- вводить отрицательный отдельный бонус.

Налог и комиссия хранятся положительными величинами удержаний.

При старте нового 14-дневного периода cumulative hours/orders могут сброситься.

## 20. Обязательные тесты

### Test A — темп

Ввод:

- `H = 179`;
- `O = 345`.

Ожидание:

`visiblePace = 345 / 179 ≈ 1.92737`

Главный экран показывает только эту цифру.

### Test B — оффлайн-запас

```text
offlineReserve =
345 / 1.80 - (179 + 59/60)
```

Результат должен быть преобразован в часы/минуты.

### Test C — дельта

Вчера:

`153 ч`

Сегодня:

`165 ч`

Показать:

`Изменение отображаемых часов: +12`

Не писать:

`Сегодня отработано ровно 12 часов`.

### Test D — экспорт

После ввода нескольких дней кнопка `Экспорт для ChatGPT` создаёт валидный `.md` файл со:

- текущим состоянием;
- полной финансовой сводкой;
- всеми дневными строками периода;
- формулами и правилами округления.

RAW в файл не попадает.

### Test E — прошлое закрытие

Для аудита:

- paidReward = `25 900 ₽`;
- finalAdjustment = `19 280.40 ₽`;
- ставка = `360 ₽/ч`.

```text
trueFinalHours =
(25 900 + 19 280.40) / 360
≈ 125.5011 ч
```

Экранные `125 ч` совместимы с `floor(trueCumulativeHours)`.
