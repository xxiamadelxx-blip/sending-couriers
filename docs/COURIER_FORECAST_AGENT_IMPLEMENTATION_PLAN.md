# ТЗ и план реализации: автономный прогноз в «Доход курьера»

**Версия:** 1.1  
**Дата:** 22.10.2026  
**Тип документа:** ТЗ интеграции в существующий Android-проект; поправка 1.1 — персональный режим работы и корректная экспозиция времени  
**Результат:** обновление **существующего** Android-приложения «Доход курьера» с APK, тестами, журналом проверок и документацией. **Не создавать отдельное приложение вместо интеграции.**

> **Задание агенту:** реализуй описанные ниже функции в существующем «Доходе курьера», не нарушая учёт доходов и не теряя сохранённых записей. Работай по этапам M0–M9. На каждом этапе представь фактические доказательства работоспособности, PASS/FAIL и исправления. Если конкретный технический путь невозможен, обоснуй результат проверкой и переходи к предусмотренному fallback; не зацикливайся на одном блокере. Результат этапа разработки подтверждается кодом, автоматическими тестами и сборкой. Итоговый функционал захвата экрана подтверждается реальным Android-устройством. Запрещено выдавать макет, заглушку или симуляцию за работоспособную функцию.

## 0. Непереговорные требования

1. **Полностью автономный расчёт прогноза:** без LLM, без ChatGPT, без платных API, без обязательного интернета. Статистика и расчёты выполняются на Android-устройстве. Для погоды интернет разрешён; в офлайне показывается последний кэш с отметкой актуальности.
2. **Интеграция, а не замена:** сохранить старые финансовые записи, логику доходов, премий, расчётных периодов, настройки оплаты, существующий стиль. Не сбрасывать базу при обновлении APK.
3. **Три новых функциональных блока:** «Прогноз сегодня», «Прогноз на 7 дней / Риски», «Импорт факта из Яндекс Про»; статистика точности в прогнозном блоке.
4. **Утренний прогноз фиксируется неизменно.** При новых данных сегодняшняя карточка обновляется, но только созданием новой версии *nowcast*. Первоначальный утренний прогноз остаётся доступен для честной оценки ошибки.
5. **Факты не выдумывать.** Нет корректных скринов/часов/заказов -> показывать «данные неполные», не подменять пропуск нулём. Не выдавать модельные значения за фактические.
6. **Погодные пиктограммы размещать только на главной:** три части суток «Утро / День / Вечер» с символами солнце / облачно / дождь / снег и минимальными температурными показателями. На экранах прогноза отдельного погодного блока **нет**. В расчётных признаках погода может использоваться.
7. **Не требовать постоянного ПК и локального Docker/Gradle.** Сборки, JVM/UI-тесты и Android-эмулятор проводить через допустимую облачную инфраструктуру/CI. APK предоставить для установки на телефон.
8. **Никаких скрытых записей чужого экрана, фонового обхода разрешений, перехвата токенов, нажатий за пользователя или вмешательства в Яндекс Про.** Только пользовательский запуск сеанса сбора отчёта и локальная обработка показанных экранов.
9. **Рабочая доступность и учёт для выплаты — две независимые оси.** Отдельно сохранять время фактической работы, офлайн/перерывы, подтверждённое ожидание заказов и часы Яндекса. Подтверждённая личная пауза без выполнения заказов не является наблюдением «спроса нет»; Яндекс при этом может продолжать начислять часы для выплаты. Не вычитать такую паузу из подтверждённого спидометра и не включать её в экспозицию модели. Технический статус «офлайн»/«новые заказы выключены» сам по себе не определяет работу: доставка уже принятого заказа остаётся WORK.
10. **Все величины оплаты и пороги версионируются в настройках по датам действия.** Ни одно историческое правило нельзя молча применить к новому периоду.
11. **Приложение предназначено для разных людей.** У каждого собственные рабочие окна, перерывы, район, часовой пояс и история. Привычки владельца исходной таблицы не являются общими настройками продукта. Требования §2.5 и §3.1 обязательны для M1–M9.

## 2. Продуктовая структура и экраны

### 2.1. Главная «Доход курьера»

Сохранить и визуально выделить:

- «Общий доход» и «Осталось получить» как отдельные крупные показатели;
- премии в рублях, учитываемые часы, число заказов, общий темп и условия получения выплаты;
- явный индикатор выполнения **минимума учитываемых часов**, если такое требование действует в выбранных настройках (ранее отмечался минимум 80 ч);
- верхний правый переключатель 🌙/☀️, настоящая экономичная AMOLED-тема с чёрными фонами и полноценная светлая;
- компактный блок погоды по рабочей местности: `Утро ☀️ +…°` | `День 🌧️ +…°` | `Вечер ☁️ +…°`; снег ❄️ по условию. При отсутствии связи обозначить возраст кэша, не показывать устаревшее как текущее;
- краткую ссылку «Прогноз сегодня» с ожидаемыми заказами и статусом модели; детальные погодные показатели сюда не добавлять.

Погоду получать по выбранному человеком городу/району. Кудрово — рабочая зона владельца приложенной истории, а не обязательный район для всех; существующий выбор сохранить, новому пользователю предложить свой район. Геолокация в фоне **не обязательна**. Источник без платной подписки и с проверенными условиями использования, кеширование, обновление при доступном интернете, корректная работа без интернета.

### 2.2. Экран «Прогноз сегодня»

Основной экран текущей даты и рабочего района:

- выбранный день, **момент выпуска** прогноза, модель и её версия;
- *утренний зафиксированный прогноз* по интервалам (пример: 10:00–15:00, 18:00–22:00; реальные часы редактируются в персональном графике), общий центр и вероятный диапазон;
- факт на текущий момент: заказы, часы Яндекса, фактические рабочие интервалы, офлайн/перерывы и ожидание заказов с раздельными метками достоверности; общий темп для выплаты и темп за рабочее время показывать отдельно (§2.5);
- **обновлённый прогноз до конца дня** (nowcast): наблюдаемое + ожидаемое на оставшиеся интервалы, явное разделение факта и прогноза;
- риск не выполнить выбранную дневную задачу, запас пустых часов до безопасного и критического порога;
- лучшие / слабые интервалы **лишь если сравнительная история достаточна**;
- уровень уверенности «низкая / средняя / высокая», число сопоставимых наблюдений, baseline для сравнения, основные причины, дата последней калибровки;
- кнопки «Импортировать факт», «Добавить вручную», «История прогнозов / точность».

**Поведение:** автоматический первый прогноз за локальную дату выбранного профиля (`timezone`; у владельца исходной истории — `Europe/Moscow`) через фонового планировщика и гарантированный расчёт при первом запуске/открытии за день. WorkManager не гарантирует точной минуты, поэтому нельзя обещать генерацию ровно в 07:00 при закрытом приложении. Каждый новый подтверждённый факт обновляет наблюдаемую часть и *создаёт новую версию* nowcast, не меняя утреннее предсказание и старые версии.

Статусы чисел должны быть различимы: `ФАКТ` / `РАСЧЁТ` / `ПРОГНОЗ` / `ДОПУЩЕНИЕ`.

### 2.3. Экран «Прогноз на 7 дней / Риски»

Интерактивный недельный симулятор. По каждому из семи дней:

- день недели/дата, включатель «работаю / выходной»;
- время начала/окончания смены и, при необходимости, отдельные слоты;
- рабочие интервалы, офлайн/обед/перерывы и часы, учитываемые для выплаты; «ждал заказы во время работы» отдельно от «не работал» (§2.5). Обед может проходить онлайн или офлайн, а его учёт для выплаты задаётся отдельно;
- ползунки с шагом 15 минут + поле точного числового ввода, чтобы можно было выставить произвольные разумные значения без неудобных ограничений;
- редактируемые предположения о районе, бонусах/акциях, при наличии истории об их эффекте;
- автоматическое ожидаемое количество заказов и интервал неопределённости;
- «Сохранить сценарий», «Сбросить изменения», «Сравнить 2 сценария», редактирование распределения по дням.

Ниже — агрегаты недели **и отдельно действующего 14-дневного расчётного периода с пятницы**:

- уже подтверждённые заказы/часы + прогноз оставшихся дней;
- вероятный общий темп, прогнозные учитываемые часы, прогноз заказов;
- расстояние до минимума часов и порогов темпа, запас пустых учитываемых часов;
- при корректной калибровке вероятности `P(выполнены все условия)` и `P(темп < критического)`. При малой истории — не псевдоточные проценты, а качественный риск и честный интервал;
- предполагаемая почасовая выплата **только при выполнении условий**, отдельно чаевые/бонусы/корректировки, и уведомление «почасовой доход не гарантирован при текущем сценарии»;
- сравнение базового сценария и пользовательского варианта.

Недельная симуляция пересчитывается **сразу после движения ползунка** (с debounce, без сетевых обращений). Настройки сценария не записывать в факты и не подмешивать в обучение. Проверять непересекающиеся интервалы на поведенческой оси отдельно от признака учёта для выплаты. Подтверждённые личные паузы UNAVAILABLE исключены из экспозиции, доставка принятого заказа при отключённых новых заказах остаётся WORK. В общий темп входят только учитываемые Яндексом часы, включая начисленное время вне работы. Не складывать эти две оси как независимые длительности.

### 2.4. Экран «Импорт из Яндекс Про»

Сценарий пользователя строго такой:

1. В «Доходе курьера» нажать **«Считать отчёт из Яндекс Про»**.
2. Приложение объясняет, что будет захвачено, предлагает выбрать день и запрашивает **разрешение Android на сеанс записи/демонстрации экрана**.
3. После разрешения пользователь открывает Яндекс Про (кнопка «Открыть Яндекс Про», если установлен).
4. Пользователь показывает **спидометр / итоговую статистику**, затем **разворачивает отчёт по каждому заказу и прокручивает список до конца**.
5. Наше приложение во время сеанса считывает доступные кадры локально и распознаёт нужные поля, по возможности отслеживая смену экранов/положение прокрутки.
6. Пользователь возвращается в «Доход курьера» и завершает сеанс. Приложение показывает **сколько заказов найдено, что распознано, что не найдено, расхождения и уровень доверия**.
7. После проверок приложение **автоматически** сохраняет надёжно подтверждённые поля. В том же результате есть действие **«Уточнить время работы»**: человек задаёт фактические окна «с … до …», офлайн и обед. Точный отчёт о 14 часах не доказывает 14 часов работы. Если подтверждены только заказы/деньги/спидометр, эти поля сохраняются, а рабочая экспозиция остаётся неизвестной до уточнения; отчёт не выбрасывать и вымышленные простои не добавлять. Сомнительные значения/конфликты требуют исправления; неполный отчёт остаётся `PARTIAL`, но не заменяет прежний полный факт. Достоверность хранится по полям, не одним флагом на весь импорт.
8. Обновляются дневной факт, дневной nowcast, статистика и последующие прогнозы (утренний прогноз за прошедший день не трогать).

**Обязательные поля извлечения, только когда они реально видны:** дата отчёта, число заказов, учитываемые часы, активные часы, значения спидометра, элементы подробного списка заказов, время и суммы по каждому заказу, вознаграждение/корректировки. Если на конкретном экране нет поля, сохранить `unknown`, а не выводить из воздуха. Поля оплат и заказов финансового приложения не отождествлять без проверенной семантики (сумма за заказ ≠ гарантированная выплата ≠ чаевые).

**Предпочтительная технология:** `MediaProjection` + `ForegroundService(mediaProjection)` + локальный OCR + детерминированный парсер экранов. Запуск **вручную пользователем на сеанс**; постоянная видеозапись рабочего дня не нужна. Для Android 14+ токен разрешения одноразовый на сеанс захвата, пользовательское согласие на новую сессию неизбежно. Простое сворачивание Яндекс Про не обязано завершать уже активный сеанс; остановка, блокировка экрана, отзыв доступа и завершение процесса могут завершить его.

**OCR:** сначала технически сравнить надёжность извлечения цифр, кириллицы и списка заказов на реальных скриншотах. Не предполагать, что модель `ML Kit Text Recognition v2` полноценно понимает русский интерфейс. Рассмотреть движок, поддерживающий кириллицу офлайн, например `PaddleOCR PP-OCRv5 cyrillic/eslav mobile` с проверкой лицензии, размера, производительности, корректности встраивания в Android, либо другой проверенный локальный движок. OCR должен быть **заменяемым интерфейсом**, а не захардкоженным в UI. Шаблоны/правила экрана версионировать отдельно от прогнозной модели.

**Не считать AccessibilityService базовым путём реализации.** Это специальный доступ, у него особые требования Android/политик распространения. Его можно оценить как *необязательную альтернативу* только после документированной проверки законности, UX и надёжности; нельзя обещать «один раз выдал доступ и навсегда скрытно считывает». Не обходить `FLAG_SECURE`, технические ограничения или политики площадок.

**Конфиденциальность:** по умолчанию не сохранять видеозапись и сырые кадры. Хранить только необходимые числовые факты, техническую информацию о происхождении и при необходимости редактированный пользователем подтверждённый фрагмент; персональные данные клиентов, адреса, телефоны и содержимое уведомлений не записывать. Запрет отправки кадров в сеть; явная кнопка «Остановить захват» и видимое системное уведомление во время сеанса. Экспорт диагностических кадров только по отдельной команде пользователя с маскированием.

**Надёжность:** не создавать дубликаты при повторном пролистывании, повторном запуске и импорте одного дня. По возможности использовать ID заказа; при отсутствии ID — устойчивую комбинацию полей и ручную проверку возможных совпадений. Иметь правила обнаружения начала/конца списка, фильтр кадров без новых данных, маркеры «полный/неполный» и сверку количества строк с итоговым числом на спидометре. Не списывать несогласованность OCR как корректный факт.

### 2.5. Персональный режим работы и уточнение после импорта (поправка 1.1)

**Цель:** любой человек может настроить свой режим, а после загрузки отчёта указать: «из 14 часов я работал 9, с такого-то по такое-то время». Модель не трактует оставшиеся часы как слабый спрос.

**Настройки → Мой рабочий режим:**

- Рабочий район и часовой пояс; дни работы/отдыха; несколько рабочих окон на каждый день недели. Числа 9, 10, 14 или 14,5 часов и график 09–15 / 18–22 не фиксировать в алгоритме для всех пользователей.
- Обед и другие перерывы: любое количество, длительность в минутах и точные начало/конец. Допускаются 0 минут и работа без офлайна; один час обеда — только пользовательский выбор, не обязательный вычет. Шаблоны «без перерыва», «обед», «свой график» — редактируемые заготовки.
- Для перерыва отдельно: **готов работать / личная пауза без доставки (UNAVAILABLE) / неизвестно**. Обед с готовностью принимать заказ остаётся WORK. Подтверждённый обед без готовности и без выполнения заказов исключается из экспозиции. Выключение новых заказов не исключает время завершения уже принятой доставки. Технический онлайн/офлайн платформы хранить отдельно, он не задаёт эти состояния автоматически.
- Отдельный параметр сценария: **начисляются ли часы Яндекса, когда не работаю: да / нет / не знаю**. Это предположение будущего сценария, не команда переписать факт спидометра. Фактический учёт берётся из подтверждённого источника/правила.
- Пользователь может применить шаблон к будущим дням или сохранить отдельное исключение конкретного дня. Дата начала действия и версия профиля обязательны. Новый шаблон не переписывает старые факты и зафиксированные прогнозы.
- Персональная база и калибровка хранятся на устройстве. Для распространения приложения обязательная регистрация/сервер не нужны. Историю владельца приложенного XLSX не встраивать в новую установку: её импортирует только владелец явным действием.

**После импорта отчёта / при ручном вводе:**

1. Показать дату, найденные заказы и деньги, часы Яндекса и длительность слота как разные показатели с источниками.
2. Предложить редактируемые интервалы **«Фактически работал с … до …»**, а также офлайн/обед. Можно добавить несколько рабочих окон и разные перерывы за день. Значения из шаблона пометить `ДОПУЩЕНИЕ`, пока пользователь не подтвердил этот день и нет фактического источника расписания.
3. Показать сумму рабочих минут. Оставшееся время пометить офлайном только после подтверждения «в остальное время не работал» либо явного источника; иначе остаток `UNKNOWN`. Одного разрыва между заказами, даже больше двух часов, недостаточно.
4. Если человек знает только суммарные 9 часов, сохранить эти 9 часов с точностью «только сумма»: не придумывать их расположение в сутках. Можно обучать дневную модель на известной сумме с соответствующим уровнем доверия; почасовую модель без границ не обучать. Простого итогового нуля заказов недостаточно, чтобы объявить каждый час нулевым наблюдением.
5. Сохранить исходный отчёт и отдельную ревизию уточнения. Повторный импорт того же дня сохраняет ручное уточнение времени; несовместимые новые сведения показываются как конфликт. Уточнение времени не дублирует заказы и не меняет суммы выплат.
6. После подтверждения пересчитать экспозицию и создать новую версию nowcast/оценки ошибки. Утренний прогноз, его `trainingCutoff` и прежние версии не изменяются. Обучение будущих выпусков использует подтверждённую ревизию; ещё неизвестные поля не заполняются шаблоном задним числом.

**Однозначные определения времени:**

| Показатель | Значение и применение |
| --- | --- |
| Длительность слота/отчётного окна | Только границы календарного окна. Из них нельзя автоматически получить часы работы или оплачиваемые часы |
| Рабочее время `workingMin` | Подтверждённая готовность работать: выполнение заказов **и** ожидание, когда человек готов принимать заказы. Именно это экспозиция прогноза количества заказов |
| Личная пауза `unavailableMin` | Подтверждённое время, когда человек не выполнял заказ и не был готов работать. Не является нулевым наблюдением спроса; может учитываться для выплаты. Статус «офлайн» платформы сам по себе этого не доказывает |
| Время на выполнении `onOrderMin` | Принятие → завершение подтверждённых заказов; для одновременных заказов — объединение интервалов. Это не всё рабочее время, паузы между заказами могут быть рабочими |
| Ожидание без заказа `availableNoOrderMin` | Только подтверждённое рабочее время готовности без выполняемого заказа. Не выводить его из неизвестных разрывов и неполного RAW-списка |
| Часы Яндекса `appAccountedMin` | Подтверждённый знаменатель темпа/условий выплаты. Не заменяется длительностью слота или личным графиком |
| Учитываемое вне работы `countedNonWorkingMin` | Подтверждённое пересечение начисляемого времени с нерабочими интервалами. Может ухудшать финансовый темп; не ухудшает оценку спроса |
| Неизвестное время | Не подтверждены режим, границы или учёт. Хранить `unknown`, не превращать в нулевой спрос, офлайн или оплачиваемую паузу |

**Контрольный пример:** окно 07:00–21:00 длится 14 часов. Пользователь подтверждает работу 09:00–14:00 и 17:00–21:00: `workingMin=540` (9 ч); подтверждает, что 07:00–09:00 и 14:00–17:00 не работал: `unavailableMin=300` (5 ч). При 27 заказах рабочий темп `27/9=3`. За эти 5 часов модель не получает наблюдений «0 заказов при доступном курьере». Если спидометр отдельно подтвердил 14 учитываемых часов, финансовый темп остаётся `27/14≈1,928571`, а не 3. Если 14 часов — только длина слота, финансовый знаменатель неизвестен до подтверждения. 5 часов не объявляются ожиданием без заказа. Паузы внутри 9 рабочих часов, когда человек был готов работать, остаются в рабочей экспозиции даже при нуле заказов.

**Инварианты:**

- `totalCounted = activeCounted + idleCounted` только если определения и исходные данные позволяют такое разложение; если есть неизвестный остаток, показывать его отдельно, не искусственно равнять. `activeMin` может быть физическим активным временем и **не обязано** механически совпадать с интервальными «учитываемыми» часами. Зафиксировать единый смысл каждого поля после аудита.
- `orders / accountedHours` — **общий темп для выплаты**; `orders / workingHours` — темп за фактическое рабочее время и база сопоставимости модели. Термин `activeHours` без проверенного смысла не использовать: он может означать время на заказах, рабочие окна или старую оценку. Длительность заказа не равна рабочей экспозиции.
- `orders / 0` не вычислять; выходной и дни с нулём заказов разрешены.
- Расчётный период исторически 14 суток, начинается в пятницу; **конкретный anchor и правила взять из действующих настроек/истории, не зашивать без проверки**.
- Миграции обратимы посредством резервной копии: старые пользовательские данные не удаляются и не обнуляются. Экспорт/восстановление базы через явное действие пользователя.
- Локальная база является рабочим источником автономного приложения. Историю `Courier Forecast` импортировать проверяемо, с idempotent-upsert и отчётом несоответствий. До согласованного переноса исходная таблица остаётся историческим эталоном, не переписывать её автоматически.
- Хранить метку происхождения: `manual`, `screen_capture`, `sheets_import`, `financial_app_existing`, а также источник/версию и факт подтверждения.

### 3.1. Инварианты интервалов, персонализации и старой истории

- Две независимые оси: режим человека `WORK/UNAVAILABLE/UNKNOWN` и учёт Яндекса `YES/NO/UNKNOWN`. Технический статус офлайн сам по себе не задаёт ни одну ось; WORK включает и готовность работать, и выполнение уже принятого заказа. Подтверждённое выполнение заказа не вырезается из экспозиции из-за отключения новых заказов. День отдыха может иметь 0 рабочих часов и ненулевые учитываемые часы; прогноз спроса на нерабочие интервалы отсутствует.
- При пересечении ручной паузы с подтверждённым временем доставки сохранить оба источника и конфликт, предложить уточнение. Заказ/его деньги не удалять, доставку не вычитать молча. До разрешения конфликтная часть экспозиции — unknown для обучения.
- Интервалы полуоткрытые `[start,end)`; соседние не дублируют минуту. Пересечения конфликтующих состояний не сохранять молча, повторные импорты дедуплицировать. Сумму считать по объединению одинаковых интервалов. Время между окнами не является автоматически подтверждённым офлайном.
- Переход через полночь указывать явными датами, разбивать экспозицию по локальным суткам. Часовой пояс пользователя хранится, не определяется местом текущего VPN. Правила расчётного периода и отнесение подтверждённых часов выплаты остаются по источнику/PaymentRules; не выдумывать их распределение из RAW.
- При полной разметке отчётного окна: `workingMin + unavailableMin + unknownMin = windowMin`. Отдельный итог спидометра не складывается с этой суммой. `onOrderMin` и `availableNoOrderMin` — разложение рабочего времени только при полном согласованном источнике; не вычитать неполный RAW из всей смены для получения «простоя».
- Каждая корректировка содержит источник и ревизию. Новая версия профиля действует на план/сценарии вперёд; факты меняются только отдельной подтверждённой правкой дня. В модели и прогнозном снимке указать применённую версию определения экспозиции. Совокупность персональных настроек другого пользователя не переносить как текущие правила нового владельца.
- В XLSX прочитаны листы «Смены» (C:E — границы и «Активные часы»), «Дневные итоги» (C:D, H, O:Q), «Настройки» (B9:B13, B19:B24, B31), «Аудит 19.10» (строка6). В них есть персональные шаблоны 09–15 / 18–22, режим14,5ч и исторические реконструкции. Это данные/допущения конкретного владельца, не универсальные константы. При импорте сохранить исходные числа и комментарии; строки с реконструированным временем не превращать в подтверждённую почасовую экспозицию. Столбец «Оффлайн-разрывы >2 ч» не доказывает фактический статус каждого промежутка.
- В исходнике прямо отмечено: границы слота 07:30–22:00 не доказывают активные или учитываемые часы («Аудит 19.10», C6:E6). При неизвестных часах исключать только неподтверждённую часть из модели, сохранять подтверждённые заказы и финансы. При неизвестном расположении 9 рабочих часов использовать дневной уровень, а не выдуманный почасовой профиль.
- При расхождении старой финансовой памятки XLSX с действующей семантикой приложения сначала зафиксировать mapping/конфликт в M0–M2. Сам импорт расписания не меняет «Общий доход», выплаты, чаевые, бонусы и удержания приложения.

## 4. Формулы и тарифы

Параметры в настройках, с версиями по датам: пример ранее действовавших значений — **360 ₽/учитываемый час, безопасный темп 1,85 заказа/ч, критический 1,80, условие 80 учитываемых часов в периоде**. Это **не утверждение об актуальных условиях**, все параметры изменяемые.

- `общий темп = подтверждённые заказы / все учитываемые часы`;
- `рабочий темп = заказы / подтверждённые рабочие часы (WORK)` (не использовать вместо общего для оплаты); отдельный темп на времени выполнения заказа возможен только как подписанная аналитика с другим знаменателем;
- `запас учитываемых пустых часов до t = max(0, orders/t - alreadyAccountedHours)`; если уже ниже порога, выводить **«дефицит до порога»** отдельно, а не просто ноль;
- `необходимые дополнительные заказы = max(0, ceil(targetPace * projectedTotalAccountedHours - projectedOrders))`, лишь для выбранного сценария;
- если темп ниже критического либо не выполнено иное обязательное условие выплаты, почасовая сумма **не является гарантированной выплатой**. Можно показывать условный расчёт «при выполнении условий» с явной маркировкой;
- денежные значения рассчитывать по действующим правилам приложения, с учётом бонусов, чаевых, выплат, корректировок и ранее принятой семантики «Общий доход» / «Осталось получить». Никогда не дублировать прибыль из заказа при импорте OCR.

Ожидаемые будущие пустые часы — **допущение сценария**, а не наблюдение. Прогноз заказов суммируется только по будущим `WORK`-интервалам конкретного профиля; личные паузы UNAVAILABLE без выполнения заказов не создают экспозицию. Технический офлайн при продолжающейся доставке не отменяет WORK. Внутри `WORK` подтверждённое ожидание без заказов — допустимое наблюдение, его нельзя вырезать для искусственного повышения темпа. Не умножать общие учитываемые часы на рабочий темп; финансовые риски рассчитываются отдельно по прогнозным учитываемым часам.

## 5. Прогнозная модель (локальная)

### 5.1. Обязательный baseline

- Сопоставимые наблюдения: **тот же день недели**, близкий интервал суток, та же/похожая рабочая зона, похожая сезонность, последние недели.
- Прозрачное взвешивание свежих данных больше старых; при малом количестве наблюдений — усадка к более широкой группе и широкий интервал.
- Нормировать заказы на подтверждённые `WORK`-минуты того же пользователя/периода/интервала. `UNAVAILABLE` не добавляет ни длительности, ни отрицательных примеров. Неизвестная длительность не становится нулём. При неизвестных границах использовать дневную, а не почасовую модель. Согласовать семантику E листа «Смены» до обучения: подписанные «активные часы» могут быть исторической реконструкцией.
- Baseline должен быть доступен рядом с выбранной моделью, а не только в отчётах разработчика.

### 5.2. Кандидаты и выбор

- Начать с простой взвешенной статистики и модели счётных данных (Poisson с экспозицией); при заметной сверхдисперсии проверять Negative Binomial.
- При достаточной фактической истории и работоспособном Android runtime рассмотреть более гибкие модели, но **не тащить Python-сервер или облачный LLM в production**. Дополнительная модель принимается лишь при лучшем temporal backtest, ресурсной пригодности и воспроизводимости.
- Вес истории, регуляризация, требования к `N`, правила уверенности и диапазоны настраиваются из результатов проверки, а не из красивой цифры.
- Учесть погоду/район/праздники/акции **только при наличии данных и доказанном улучшении качества**. Если свежая погода недоступна, использовать модель без погодного признака или явное допущение, а не подставлять вымышленное значение.
- Использовать калиброванную предиктивную неопределённость (например, бутстрэп по дням или корректную count distribution). Для недельного риска учитывать корреляцию интервалов одного дня, не выдавать независимые часы за независимые наблюдения.

### 5.3. Хронологическая проверка качества

- **Никакой оценки на обучающих строках.** Rolling / expanding origin: прошлые дни -> прогноз будущих дней, затем окно сдвигается вперёд.
- Минимальные метрики: `MAE`, `signed bias`, `WAPE/SMAPE` при корректном знаменателе и `n`; при нулевых фактах процентную ошибку для отдельного дня считать `не определена`.
- Измерять качество отдельно утренних прогнозов и nowcast. Не давать nowcast пользоваться фактами, пришедшими **позже его timestamp**.
- Метрики на уровне интервалов и дня, качество диапазонов (coverage), разбивка по дням недели при достаточном числе строк.
- Выбор новой модели только по out-of-sample качеству; сохранять предыдущую рабочую версию и уметь откатить.
- После подтверждения дневного факта автоматически построить строку `утренний прогноз -> факт -> абсолютная ошибка -> процентная ошибка (если определена) -> завысил/занизил`, затем агрегировать ошибки и обновить параметры **только для будущих выпусков**.
- Не пересоздавать задним числом старый прогноз после получения факта. Исправление факта оформлять отдельной ревизией/аудитом и пересчитывать его оценку, сохраняя прошлую запись о сравнении.

### 5.4. Риски на неделю

- Для каждого сценария прогнозировать распределение **суммарных заказов и общего учитываемого времени**, а не просто недельную сумму средних.
- Сравнивать с условиями из `PaymentRules`, включая минимум часов и пороги темпа, с учётом уже подтверждённых результатов текущего расчётного периода.
- Если прогностическое распределение достаточно откалибровано — дать вероятность и диапазон. Если нет — `низкая уверенность`, качественную оценку («низкий/средний/высокий риск») и расчётную дистанцию до порога, без неподкреплённой «точности 87%».
- Изменения ползунков никогда не участвуют в обучающей выборке, пока не стали подтверждёнными реальными рабочими данными.

Следовать **установленному** в M0 стеку. Если Kotlin/Jetpack уже используются, рекомендуемый модульный контракт:

## 8. Сквозные контрольные сценарии (обязательны)

1. **Новый день, нет интернета.** Из истории формируется утренний прогноз. Погодный кэш помечен как устаревший, прогнозные расчёты и доход работают.
2. **Прогноз утром и факт вечером.** Утренний прогноз неизменяем. После ввода факта появляется ошибка MAE-подобного сравнения и новая запись для будущего обучения. Никакого «улучшения» старого прогноза задним числом.
3. **Факт в середине дня.** Экран обновляет подтверждённые числа и nowcast; отдельный исходный утренний прогноз прежний.
4. **37 заказов / 9 рабочих ч / 14,5 учитываемых ч.** Рабочий темп `4,111...`, общий для выплаты `2,5517...`; пороги сравниваются **только с общим**. Не называть 5,5ч ожиданием без заказа и не использовать их как нулевой спрос без подтверждения состояния.
5. **Пограничные пороги.** При настройках безопасного `1,85`, критического `1,80` и часового минимума `80` корректно отличать выполнение темпа от выполнения всех условий. Рядом указать применённую версию правил.
6. **Выходной и нулевые заказы.** День сохраняется без искусственного заказа, процентная ошибка не делится на ноль.
7. **Редактирование сценария.** Поменяли пустые часы будущей среды с 0 на 4: общий темп/риск пересчитаны, но подтверждённые дневные факты и обучающая выборка не затронуты.
8. **Импорт из Яндекс Про.** Старт в нашем приложении -> системное разрешение -> переключение в Яндекс Про -> показать сводку -> открыть/прокрутить детали -> возврат -> корректная сверка -> запись в БД -> отражение на главной и в прогнозе.
9. **Повторный захват того же отчёта.** Нет удвоения числа заказов, вознаграждения или часов. Конфликты видны в интерфейсе.
10. **Недостаточно распознано.** OCR пропустил заказы/время, не определил конец списка, число заказов расходится со спидометром: статус `PARTIAL`, цифры не становятся подтверждённым эталоном автоматически.
11. **MediaProjection остановлена Android.** После блокировки экрана/потери процесса не переиспользовать старый токен; понятное сообщение и повторное пользовательское согласие на новый сеанс.
12. **Смена суток/расчётного периода, переход октябрь–ноябрь.** Нет перепутанных дат, заднего влияния на утренние прогнозы, ошибочных пересечений интервалов.
13. **Обновление APK поверх прежнего.** Старые записи, премии, выплаты, ставка, периоды и пользовательская тема сохраняются.
14. **Приложение месяц не подключено к сети.** Все локальные действия работают; не требуется логин или ответ внешнего ИИ.
15. **Маскирование.** В кадрах и диагностике не остаются имена, телефоны, адреса клиентов; кадры по умолчанию не сохраняются.

16. **14 часов в отчёте / 9 часов работал.** Окно07–21, работа09–14 и17–21, подтверждённый офлайн07–09 и14–17: экспозиция9ч, офлайн5ч. При27заказах рабочий темп3, общий27/14 только если спидометр подтвердил14ч. Никакого обучения на5ч как на нулевом спросе.
17. **Работа без офлайна.** Весь подтверждённый интервал9ч — WORK, офлайн0. Нет обязательного вычета обеда/часа и нет потери экспозиции.

20. **Только итог9ч без границ.** Сохранённый итог пригоден для дневного расчёта с источником, но не порождает ложных нулей/интервалов по часам.
21. **Персонализация без переписи истории.** Два разных пользователя: без пауз и с часовым офлайном. Один XLSX не заселяется в обе установки. Изменение шаблона влияет на будущий сценарий; закрытый факт/прогноз неизменён. Повторный импорт сохраняет ручное уточнение.
22. **Полночь, пересечения и дубли.** WORK23–02 даёт3ч, распределённых по двум локальным суткам. Повтор не удваивает длительность; конфликт WORK/UNAVAILABLE (подтверждённая личная пауза) и неполная разметка видны, не сглаживаются автоматически.
23. **Разный учёт одинакового офлайна.** При одинаковых9ч WORK и5ч офлайна прогнозная экспозиция одинакова. Если Яндекс начислил14ч одному и9ч другому, финансовые знаменатели различны, но первый человек не считается работавшим при нулевом спросе5ч.

24. **Новые заказы выключены, доставка продолжается.** Курьер отключил приём в14:00, но вёз принятый заказ до14:25. Эти25мин — WORK. Если ручной обед помечен14:00–15:00, зафиксировать пересечение и запросить уточнение, сохранить заказ/деньги и оба источника; до разрешения не использовать конфликтную часть как нулевой спрос или подтверждённый офлайн.

## 9. Принятие OCR: какие тесты нужны

Два независимых набора:

**A. Golden fixtures:** размеченные вручную скриншоты/кадры разных состояний Яндекс Про (сводка, открытый заказ, детали, начальная/средняя/конечная часть списка, повтор прокрутки, плохой кадр, разные размеры текста). Разметка содержит только обезличенные поля, эталонное число и суммы. Прогнать *ещё не виденные при настройке parser* кадры, выдать `precision/recall` по распознанным заказам, точность критичных чисел, список false positives/negatives и конфликтов. Нужные пороги PASS назначить **до** финального прогона с учётом фактической доступности образцов.

**B. Device E2E:** Android 15 / OnePlus либо совместимый доступный реальный аппарат + облачный эмулятор для платформенной регрессии. Проверить разрешение MediaProjection, начало и остановку, возврат в приложение, прокрутку списка, энергопотребление и факт попадания извлечённых полей в БД. При отсутствии реального устройства **не писать**, что устройство протестировано. Тест на эмуляторе отдельно от device test.

Неполные и сомнительные значения не должны автоматически становиться `CONFIRMED`: система должна иметь высокую точность **подтверждённых** фактов даже ценой большего числа `PARTIAL`.

## 10. Формат промежуточных результатов и независимая проверка

Для каждого этапа создать `docs/acceptance/MX.md`:

```text
Этап: MX
Коммит / PR:
Сделано (только реально):
Тесты (команды, ссылки на CI, артефакты):
Ожидаемый результат -> фактический результат:
PASS / FAIL / PARTIAL:
Известные проблемы и воспроизведение:
Исправления и повторный прогон:
Следующий независимый этап:
```

**Gauntlet Loop:** реализация -> независимый тест/ревью (не тем же набором self-check assertions) -> найденные ошибки -> исправление -> повторный прогон. Фактические скриншоты/логи и артефакты прикладывать. Если проверка не состоялась, статус `NOT VERIFIED`, а не PASS.

Минимальный CI следует фактическому стеку: воспроизводимая сборка существующего проекта (для базы1.6.1 — build.py + SDK35), unit-tests, static checks, миграционные тесты действующего JSON-хранилища/БД, тесты интервалов/персонализации, parser fixtures, временные backtests и UI tests на эмуляторе, где доступен. Gradle/Room обязательны только если они реально используются, не требовать переписывания стека ради проверки. Зафиксировать версии зависимостей и лицензионные условия встроенных OCR-моделей. Секретов/ключей в APK нет.
