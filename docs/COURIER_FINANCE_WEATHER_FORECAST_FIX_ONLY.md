## 1. Неприкосновенные ограничения

1. **Никакого редизайна.** Сохранить действующее оформление и расположение финансовых блоков. Разрешены только точечные правки видимости/подписей необходимого функционала в существующем стиле.
2. **Никакого обязательного ежедневного подтверждения с 21 августа.** Один импорт, автоматическая оценка достоверности, уточнение только действительно спорных отдельных дат/полей.
3. **Никакой обязательной анкеты на семь дней.** Не требовать район, часовой пояс, рабочие окна и личные перерывы перед каждым прогнозом. Внутренние параметры по умолчанию и известная история используются автоматически. Изменить их можно необязательно и отдельно.
4. Не смешивать **активное время**, **пустое, но учитываемое Яндексом время** и **полные часы слота**. Наличие 14 часов слота не доказывает 14 учитываемых часов.
5. **Не изменять старые прогнозы задним числом.** Новая версия прогноза после поступления факта хранится отдельно от исходного утреннего.
6. Без ChatGPT/Groq/Gemini/платных API для расчёта. Прогноз заказов выполняется локально. Для получения *свежей погоды* допустим интернет; без него используется корректно помеченный кэш.
7. Не ломать финансовый учёт, существующие выплаты, начисления, 14-дневные периоды, бонусы и экспорт. Входящая RAW-история не должна заменять подтверждённый финансовый факт без сверки.
8. **Отдельная вкладка «Прогнозы» была ранее запрошена.** Если она добавляется в этой правке, использовать ровно текущий стиль нижнего меню, не создавать шестую тесную вкладку и не терять «Калькулятор»: обеспечить его доступность через существующий пункт меню/настройки. Это **точечная правка навигации, не редизайн**. Пока изменение не согласовано отдельно, сохранить текущий доступ к прогнозу с «Обзора».
9. Не добавлять в этот объём: разработку иконки, экрана запуска, новую систему визуальных компонентов, OCR, видеозапись Яндекс Про, глобальную переделку навигации и полноценный мастер настройки графика. Их можно вести отдельными задачами.

## 2. Погода: исправить уже существующий модуль

### Факт по коду APK

- `assets/www/weather.mjs`: функции `weatherCache`, `weatherParts`, `weatherSymbol` существуют; берутся три времени: **09:00, 14:00, 20:00**.
- `assets/www/app.mjs`, `weatherWidget()` и `refreshWeather()`: виджет и загрузка блокируются при `!profile.weatherEnabled || !profile.weatherCity`.
- `assets/www/forecast-ui.mjs`, `profileView()`: присутствуют технический флажок «Погода на главной» и поле «Город для погоды»; их настройка не должна быть условием работы обычного пользователя.
- Взаимодействие с Open-Meteo уже предусмотрено в сборке. Его надо исправить и протестировать, а не заменять без необходимости.

### Реализация

**W-01.** Показать существующий погодный блок на экране **«Обзор»** независимо от флажка `weatherEnabled`. Убрать этот флажок из обязательного сценария. **Не показывать район/город строкой в блоке.**

**W-02.** Местность для прогноза определить при миграции **один раз** из сохранённого профиля/достоверного импорта. Для текущей персональной истории ожидаемая местность — Кудрово; для распространяемого приложения не жёстко прошивать Кудрово всем пользователям. Если местность действительно неизвестна и доступ к геолокации не предоставлен, предложить одно необязательное действие в «Настройках», не блокировать финансовый экран.

**W-03.** Три части суток отображать компактно, в существующем блоке:

| Утро | День | Вечер |
|---|---|---|
| значок + температура | значок + температура | значок + температура |

Использовать фактический прогноз из Open-Meteo с указанной зоной, а не придумывать температуру. Нет погодных карточек на экранах «Прогноз» и «Неделя».

**W-04.** Исправить WMO mapping: ясная погода → солнце, облачная → облако, дождь/морось/ливень → дождь, снег/снежные заряды → снег, гроза → соответствующая пиктограмма. Для тумана допустим отдельный нейтральный значок. Код осадков не должен давать неверный значок.

**W-05.** Загрузка автоматически при открытии «Обзора» и при устаревшем кэше (порог свежести в текущем коде 6 часов). Не делать бесконечных сетевых попыток и не замораживать интерфейс. В офлайне показывать последнюю известную погоду **с пометкой устаревания**; если кэша нет, нейтральное «Погода недоступна» без ложных данных.

**W-06.** Проверить временную зону `Europe/Moscow` для нынешней рабочей истории и корректное разбиение на локальные утро/день/вечер. Локальные настройки другого курьера должны обрабатываться корректно.

**W-07.** Подтверждённая погода может быть дополнительным признаком модели лишь после проверки улучшения ошибки прогнозов. Отсутствие погоды **не блокирует** локальное прогнозирование.

### Приёмка погоды

- `PASS`: свежая установка/обновление, где не заполнено поле города в форме «Мой рабочий режим», тем не менее показывает погоду при известной местности из профиля/истории.
- `PASS`: три части суток, значки соответствуют входным WMO-кодам; нет погодного блока внутри вкладки/экрана прогнозов.
- `PASS`: после отключения сети приложение не падает, показывает предыдущий кэш и не выдаёт его за свежий.
- `FAIL`: нужно включить чекбокс или заново вводить район ради погодного виджета.

## 3. История и факты: привести данные в состояние, пригодное для обучения

### Факт по коду

- `assets/www/forecast-import.mjs`, `parseWorkbook()` переносит `Дневные итоги`, `Смены`, `Заказы RAW`.
- Для загруженных дней `workConfirmed` по умолчанию `false`, даже когда значение `workingMin` распознано.
- `assets/www/forecast.mjs`, `trainingRows()` отбрасывает все дни без `workConfirmed===true`.
- `assets/www/forecast-import.mjs` переносит лишь часть RAW-полей. Отдельные реестры **«Прогнозы», «Точность», «Модели», «Финансовые правила»** не попадают в текущий прогнозный импорт.

### Реализация

**D-01.** Выполнить миграцию существующего состояния без удаления пользовательских финансовых записей. Перед изменением формата сделать тестовую копию данных, проверить восстановление и идемпотентный повторный импорт.

**D-02.** Импортировать позаказную историю с датой, временем события, номером заказа, по возможности временем принятия/доставки, источником, полнотой и отметкой уверенности. Сохранять 2 разных заказа с одинаковым временем, когда есть доказательства их отдельности. Не удалять повтор только по совпадению минуты.

**D-03.** Для каждого поля фиксировать тип источника: `CONFIRMED`, `RECONSTRUCTED`, `UNKNOWN`, `CONFLICT`. **Не превращать** реконструированные часы в подтверждённые. Но достоверные часы с распознанным источником не должны требовать ручного подтверждения всех исторических дат.

**D-04.** Не принимать отсутствие позаказных деталей за ноль заказов. Если известно 33 заказа, но у части нет времени принятия, сохранять 33 заказа, помечая частичность временных полей.

**D-05.** Импортировать прежние снимки прогнозов и результаты точности как **исторический реестр**, без перезаписи и без подмешивания уже известных фактов в прошлые выпуски. Хранить исходный прогноз отдельно от итогов, даже если в Excel в одной строке позже заполнено поле «Факт».

**D-06.** Если схема Excel неоднозначна, выдавать компактный отчёт «загружено / частично / конфликты», а не просить пользователя открыть каждый день из архива и нажать «подтвердить».

### Контрольный пример

В исходном реестре за **18.10.2026** указано **33 заказа** и **33 записи в «Заказы RAW»**. Время рабочих и учитываемых часов за этот день **не подтверждено**. После импорта в локальной истории должны остаться 33 заказа и 33 RAW-события, а часы — **неизвестными**. Это не ошибка самого факта, но повод не вычислять ложный темп за этот день.

**Важно:** событие с отметкой времени ещё не доказывает час фактической доступности курьера. Для почасовой скорости `заказы / часы` требуется подтверждённое или обоснованно оценённое время под риском заказа. Не считать весь промежуток от первого до последнего заказа непрерывной работой без источника.

## 4. Автономная модель прогноза заказов

### Факт по коду

Текущая версия `FORECAST_VERSION='local-exposure-1'` вычисляет обобщённый дневной показатель `orders / workingMin` с повышенным весом последних дат, а прогноз по окнам распределяет по **доле длины окна**. Время отдельных заказов в `predict()` не входит. Модель Poisson / Negative Binomial в переданном APK **не обучена и не проверена**.

### Исправление

**F-01.** Сохранить воспроизводимый простой baseline: сравнимые дни недели + фактическая экспозиция + более высокий вес последних наблюдений.

**F-02.** Строить показатели по **дню недели и часу**, затем при достаточном объёме по 30-минутным слотам; явно хранить количество наблюдений, пропуски и источник экспозиции. Не дробить редкие слоты до искусственной точности. Сглаживать к более широким группам, если данных мало.

**F-03.** Отдельно учитывать:

- `orders / activeHours` — продуктивность фактической работы;
- `orders / accountedHours` — общий темп для условий оплаты;
- невыполнявшееся, но учитываемое время — только когда этот факт подтверждён;
- отсутствие записи/неизвестное время — **не ноль заказов и не ноль часов**.

**F-04.** Реализовать локальные модели счётных данных: сначала Poisson с offset на подтверждённую экспозицию; Negative Binomial при доказанной сверхдисперсии и достаточной истории. Более сложные методы только если реально обучены, имеют валидацию и улучшают ошибку. Не употреблять в UI и отчётах название модели, которая фактически не обучалась.

**F-05.** Обучение и выбор только на прошедших датах относительно прогнозируемой. Использовать rolling/walk-forward: история до даты D → прогноз на D → затем раскрытие факта. Сравнивать модель с baseline по MAE, WAPE (когда знаменатель определён), систематическому смещению и покрытию прогнозного диапазона.

**F-06.** Если мало подходящих наблюдений, показывать «Недостаточно данных» или честный широкий диапазон с низкой уверенностью. Не создавать псевдоточные числа, проценты и «лучшие часы» из одного аналога.

**F-07.** Погода/сезон/акции как предикторы только при наличии подтверждённой истории и доказанном выигрыше на временном тесте. При потере интернета модель должна продолжать работать без погодного признака.

**F-08.** Сохранять версию алгоритма, дату обновления, количество обучающих наблюдений, временной cutoff и ошибку на валидации. Автоматическое переобучение после новых фактов не должно изменять архив прогнозов.

## 5. Прогноз на сегодня и проверка точности

**T-01.** При первом открытии приложения в новый день автоматически сформировать **утренний прогноз** (если достаточно данных). Он неизменяем. Периодическая фоновая проверка допустима, но нельзя обещать запуск в точную минуту, если Android ограничит фоновые работы.

**T-02.** После внесения фактических заказов/часов обновлять **прогноз оставшегося дня (NOWCAST)**; выводить его отдельно от исходного прогноза, не выдавать новый прогноз за «утренний».

**T-03.** После окончательного факта дня записывать прогноз, факт, абсолютную и процентную ошибку, направление завышения/занижения; проверять, попал ли факт в диапазон. Процентная ошибка не определяется при нулевом факте.

**T-04.** Отдельно считать MAE модели, MAE baseline, bias и долю попаданий в интервал по прошлым *независимым* дням; хранить оценки из прошлого и новые оценки. Все показатели рассчитывать из фактических записей, не из демонстрационных значений.

**T-05.** Если план работы на сегодня неизвестен, использовать обоснованный типовой график из истории **только как помеченное допущение** для прогноза. Не требовать заполнения семи карточек. Если прогноз количества заказов без плана необоснован, показать, что нужна длительность работы, а не выдумывать результат.

## 6. Недельные сценарии и пороги без усложнения интерфейса

**R-01.** В существующем экранe недельного прогноза оставить для обычного пользователя **ровно два основных регулируемых показателя**:

1. **Активная работа** (часы фактической доступности для заказов).
2. **Полный слот** (вся длительность присутствия/периода приложения).

Остальные технические параметры не должны быть обязательными; существующие финансовые правила работают автоматически. Это упрощение поведения текущей функции, **не редизайн внешнего вида**.

**R-02.** Полный слот **не равен** учитываемым Яндексом часам по умолчанию. Если режим учёта неизвестен, показать условный расчёт с явным условием, не рассчитывать «гарантированную» оплату по неподтверждённым часам.

**R-03.** Прогноз заказов из модели должен зависеть от активного времени, дня недели и известных типичных рабочих интервалов. Два одинаковых числа активных часов в разные дни не обязаны давать одинаковый прогноз. Когда точное время работы неизвестно, снижать уверенность и отмечать допущение.

**R-04.** Использовать целевой безопасный темп **1,85** и критический порог **1,80** по метрике `orders / accountedHours`. Учитывать 2-недельный период с пятницы и реальные финансовые правила соответствующего периода. Проверять минимум часов по сохранённой версии правил, **не считать его вечной константой без проверки**.

**R-05.** Выводить: ожидаемые заказы и диапазон (если модель позволяет), общий темп, запас учитываемых пустых часов, дистанцию до порогов, качественный риск; числовую вероятность только после калибровки.

**R-06.** **Пример только арифметики, не прогноза спроса:** при 6,5 часа активной работы и 14 часах полного слота разница = 7,5 часа неактивного времени. **Если все 14 часов действительно учитываются**, для темпа ≥1,85 требуется `ceil(14 × 1,85) = 26` заказов, для ≥1,80 требуется `ceil(14 × 1,80) = 26` заказов. Пока модель не обучена, не подставлять «ожидаемые заказы» из воздуха.

**R-07.** Ползунки и сценарные прогнозы никогда не превращать в исторические факты и не включать в обучающую выборку.

### Протокол Gauntlet Loop

На каждом этапе: **реализация → автоматические тесты → независимая проверка → исправление → повторная проверка**. Максимум три цикла исправления одной проблемы. Если сохраняется блокер, отметить `FAIL/BLOCKED`, указать лог и перейти к следующей независимой задаче. После `PASS` немедленно следующий этап. Не принимать утверждения «всё работает» без скриншота, логов, теста, установленного APK и реальных проверенных данных.

### Дополнительные обязательные регрессии

1. Новый APK устанавливается поверх старого с сохранением package ID, подписи и данных, либо несовместимость заранее документирована. **Не удалять установленное приложение и не очищать данные**.
2. Погода без интернета, отсутствие местности, серверный сбой, смена даты, старый кэш.
3. Данные за 18.10: 33 заказа / 33 RAW; без фиктивных часов. Два заказа в одну минуту сохраняются отдельно.
4. Архив с 21.08 доступен после импорта **без 60+ ручных подтверждений**.
5. Изменение сценарных ползунков не меняет финансовые факты и архив прогнозов.
6. Утренний прогноз остаётся таким, каким был создан до факта; изменение модели впоследствии его не переписывает.
7. Работа offline: все расчёты и история доступны, погода — только кэш с честной отметкой.
8. Общее оформление приложения визуально идентично предыдущей версии за исключением разрешённых точечных функций. **Никаких новых иконок приложения, splash, тем, карточек или перестройки существующих финансовых экранов**.

## 9. Что вернуть пользователю после разработки

1. Ссылку на **готовый APK**, не прототип.
2. Короткое видео/скриншоты «Обзор с погодой» и «Прогноз сегодня / Неделя» в прежнем оформлении.
3. Отчёт импорта: дат и RAW-событий, подтверждённых/неизвестных часов, конфликтов, количества пригодных наблюдений для модели.
4. Протокол обучения: реально применённые модели, дата, train/test split, MAE, baseline MAE, bias, охват диапазонов.
5. PASS/FAIL каждого этапа, доказательство установки поверх текущей версии и сохранности данных.
